# 学习闭环

## 1. 什么时候必须记录 learnings

出现以下任一情况，就应记一条 learning，而不是只在当次聊天里口头总结：

- 误路由：本应先找 owner，却交给了 generic 或下游单元
- 误判执行方式：
  - 本应直调已有 owner/runtime，却新开了泛化子任务
  - 本应新开守护执行单元，却错误地留在 inline
- 恢复失败：状态不够、checkpoint 不足、只能靠重放聊天上下文
- 重复重试：同类故障、同类误判多次出现
- 新发现了更稳定的 dispatch / recovery 模式

## 2. 记录什么

记录内容保持简短，但要可反向改规则：

- 任务类型
- 当时选择的执行方式
- 为什么这是误判或低效路径
- 正确应该怎么路由 / 怎么恢复
- 下次可复用的判断信号

避免写成空泛结论，例如“以后更小心”。要能直接改进规则。

## 3. 如何把 learning 反向写回 skill

如果同类误判 recurring，就不要只记笔记；应回写 guardian-executor：

- 更新 `SKILL.md` 的执行方式判断或禁止项
- 更新 `references/task-routing.md` 补充触发信号
- 更新 `references/interruption-and-recovery.md` 补充 stale / recovery 判法
- 必要时补一个更具体的例子，减少主代理自由发挥空间

简单原则：

**一次失误可以先记；重复失误必须改规则。**

## 4. 执行后复盘的最低要求

任务完成或失败后，快速问三件事：

1. 这次执行方式选对了吗？
2. 如果中断，现有状态足够恢复吗？
3. 有没有出现重复误判，值得写进 skill？

如果答案是否定的，就补 learning。

## 5. 这个 skill 的角色

guardian-executor 不只是执行器，也是调度经验的沉淀层。

它应持续吸收：

- 哪类任务该直调 owner
- 哪类任务必须新开专用单元
- 哪类任务其实可以 inline
- 哪些恢复方式最稳
- 哪些状态字段不够用

目标不是写很多文档，而是让后续调度越来越少误判、越来越少重跑、越来越少靠用户纠正。
