# 任务归属判断与 Owner-Aware Routing

## 目录

1. UI-only 任务
2. Domain-owned 任务

## 1. UI-only 任务

满足以下条件时，可判为 UI-only：

- 只改视觉样式、颜色、间距、排版、组件布局
- 只改已确定文案的展示位置或展示形式
- 只做前端交互、页面适配、响应式、展示映射
- 不改变字段定义、指标含义、命名标准、业务解释

**路由规则：**
直接交给前端 / 页面执行单元即可。

## 2. Domain-owned 任务

满足以下任一条件，就属于 domain-owned，而不是前端兜底任务：

- 需要统一命名、缩写规则、标准别名
- 需要决定字段、因子、策略、账号、指标的正式名称
- 需要解释“这个东西是什么 / 为什么这样命名 / 它怎么来的”
- 需要给出因子逻辑、策略归因、分析依据、数据口径
- 需要判断某个概念应由哪个系统/后端/领域负责
- 需要 owner 确认，而不是只做页面文案润色

**路由规则：**
先交给对应 owner agent / 领域执行单元，先产出：

- 统一命名
- 业务定义
- 解释说明
- 归因或分析依据
- 对下游可消费的结构化产物

在这些产物明确之前，前端执行单元不能自行定义语义。

## 3. Mixed cross-layer 任务

当一个需求同时包含：

- 上游语义 / 命名 / 解释 / 归因
- 下游页面展示 / 交互 / 落位 / 适配

它就是 mixed cross-layer 任务。

**禁止做法：**

- 整包丢给一个前端子会话
- 让前端先拍一个 display label，再回头逼后端或 owner 对齐
- 把“文案改短一点”误判成纯 UI 任务，而忽略其背后的命名权和语义权

## 4. 固定拆分顺序

对 mixed cross-layer 任务，按下面顺序拆，顺序不要反：

### 阶段 A：上游 owner 单元

先让 owner agent / 领域执行单元完成：

- 名称标准化
- 语义定义
- 逻辑描述
- 归因说明
- 数据口径确认
- 输出给下游消费的字段/映射/说明

### 阶段 B：下游展示单元

再让前端 / 页面执行单元基于阶段 A 的产物完成：

- 页面字段展示
- tooltip / 帮助文案 / 卡片说明
- 组件标题、表头、展示映射
- 交互与视觉适配

## 5. 必须先找 owner agent 的触发信号

只要需求里出现下面任一类信号，就先找 owner，不要先找前端：

- “简化名字，但不能丢语义”
- “统一命名”
- “这个因子/策略/账号到底是什么意思”
- “给用户解释这个东西怎么来的”
- “基于什么分析得出的”
- “后端字段名/产物名该怎么定”
- “先确认负责方 / owner 是谁”

简单记法：

**凡是改的不只是‘显示出来的字’，而是‘这个字背后的定义’，就先走 owner routing。**

## 6. 接近真实问题的例子

### 例子：因子名、模拟账号名的简化与说明优化

用户表面上可能说的是：

- 因子名太长，帮我简化一下
- 模拟账号名不好懂，改得更清楚一点
- 页面上补一句说明，让用户知道这个因子怎么挖出来的

这类需求**不能直接交给前端子会话整包处理**。

原因：

- “简化”不是单纯缩短 display label
- 因子名和账号名承载的是后端/策略/研究语义
- 说明文案需要回答：这个因子基于什么分析、怎么挖掘出来、为什么这样命名
- 这些都属于 owner 的语义职责，不属于前端自由发挥

正确拆法：

1. **先交给因子 owner / 策略 owner agent**
   - 收敛正式名称
   - 给出可展示简称
   - 补齐逻辑描述、来源说明、归因依据
   - 形成统一命名与说明结构

2. **再交给前端执行单元**
   - 消费统一后的简称、正式名、tooltip、说明文案
   - 做页面展示、交互落位、视觉优化

一句话判断：

**如果用户希望知道“这个因子到底是什么、怎么得来的”，那就不是前端先动，而是 owner 先定。**
